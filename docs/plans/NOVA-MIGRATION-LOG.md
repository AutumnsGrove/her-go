## Step log

### Step 2 — embeddings on OpenRouter (`a1e…`, see `git log`)

- **Live check, not docs:** `POST https://openrouter.ai/api/v1/embeddings` with
  `perplexity/pplx-embed-v1-0.6b` returns **1024** dimensions (Nova's docs happen to agree, but the
  call is the evidence). Real `embed.Client` against it: `IsAvailable()` true, `SimilarText` on a
  paraphrase scored 0.888 vs 0.032 for an unrelated sentence.
- **Dimension guard** (`memory/vec.go`): opening a store whose `vec_memories`/`vec_moods` were created at a
  different width now fails with `*VecDimensionMismatchError` and the fix in the message. Escape hatch is
  `memory.AllowVecDimensionMismatch()`, used only by `her reembed`. Functional options keep all 28 existing
  `NewStore` call sites untouched.
- **`her reembed`** (`cmd/reembed.go` + `memory.ReembedAll`): drop+recreate both vec tables at the configured
  width (one transaction), then re-embed every active memory (tags vector + text vector) and every
  non-superseded mood entry (note + labels, the same string `mood/agent.go` embeds). Idempotent, resumable,
  failures counted and skipped rather than fatal, `--dry-run` prints counts + an estimated token cost.
- **Verified end to end on a seeded temp DB** (`/tmp/reembed-probe.db`, never a real `her.db`):
  768-dim DB → guard fires on a plain command → `reembed --dry-run` reports `float[768]` → `reembed`
  rebuilds to `float[1024]` and re-embeds 2/2 → reopening passes the guard. Sim details in the log below.
- **Threshold calibration (step 2.4) — measured, then left alone.** Real calls against the new model:
  - *content* paraphrase pairs (duplicates): 0.70, 0.70, 0.77, 0.87, 0.95
  - *content* distinct-but-related pairs: 0.51, 0.55, 0.55, 0.62, 0.66, 0.69
  - *tag* vectors (the primary dedup input): identical 1.00, same tags reordered 0.834, same topic different
    noun (cats/pets vs dogs/pets) 0.833, unrelated 0.25–0.61
  At 0.85 the tag path misses a reordered-tag duplicate (0.834) but the text path catches high-similarity
  paraphrases; dropping to 0.80 would start rejecting *legitimately different* same-topic memories
  (cats/pets/names vs dogs/pets/names is 0.833). **Kept `similarity_threshold: 0.85` and
  `max_semantic_distance: 0.45` unchanged.** The dream-cycle merge already cleans up whatever slips
  through, and rejecting a true new memory is the worse error. Flagged for revisiting against
  `memory-a-thon` / `contradiction-canary` on real data — not hand-tuned off an 11-pair sample.
- **Deviation:** plan §2.5 wanted `embedding-a-thon`, `memory-a-thon`, `contradiction-canary`,
  `card-scoped-recall` run here. They are run in step 4 instead (same suites, cheaper, and on the MiMo 2.6
  stack the baselines are captured on) — running them twice would double the spend for no extra signal.

### Step 3 — MiMo 2.6

- **Prices verified live** (per 1M tokens, in/out/cache-read): `mimo-v2.6-pro` 0.435/0.87/**0.0036**,
  `mimo-v2.6-flash` 0.14/0.28/**0.0028**. Both cheaper than the 2.5 models they replace
  (`2.5-pro` 0.48/1.80/0.096, `2.5` 0.40/2.00/0.080), and cached reads drop ~25x. Both expose a
  `xiaomi/fp8` endpoint, so `provider.order: [xiaomi/fp8]` still resolves.
- **No local cost table exists** (step 3.2): every cost figure comes from the provider's `usage` block, so
  there was nothing to move into config. Nothing to update.
- **`tool_choice: "required"` check (step 3.4) — worth knowing before step 8.** Six trials each against
  `xiaomi/fp8`, `tool_choice: "required"`, two trivial tools:
  - `mimo-v2.6-pro`: 6/6 returned tool calls.
  - `mimo-v2.6-flash`: **4/6** returned tool calls; one `finish_reason: length` (it burned the budget on
    reasoning) and one `finish_reason: stop` with plain text and no tool call.
  - `mimo-v2.5` (control): 6/6.
  - **Follow-up evidence (step 4 baselines):** two identical-stack `schedule-crud` runs, legacy loop, both on Flash.
    Run 1 completed all 6 turns in 11–19 tool calls each. Run 2 had three turns stall for ~250s, one turn burn
    48–49 tool calls, and all three end without a `done` (the gateway's fallback reply covered the user).
    June's 2.5-era reports of the same suite top out at 12 tools per turn. **Conclusion: `driver.model` is now
    `xiaomi/mimo-v2.6-pro`** in `config.yaml.example` and the laptop config — Flash stays the background-agent
    model. Pro is ~3x Flash per token but still cheaper than the 2.5 Pro it replaces. This is a deviation from

    evidence of the Flash instability, and `base3`+ are the authoritative baselines.

  `config.yaml` sets `driver.require_tool_choice: false`, which hides the problem locally; the Pi uses the
  default (`true`). **Kept Flash for the driver** per plan Q5 and made this a watch item for the driver sims

  `provider.ToolDef`, `ProviderRouting`→`openrouter.Routing.Options()`, `session_id`/`reasoning`→
  `ProviderOptions`, `EmptyToolCallContent: true` to keep `"content": ""` on tool-call-only assistant
  messages (delta D7 — prompt-cache bytes).
- Deliberately preserved at the client level: her-go's `isRetriable` policy plus the fallback model, and the
  truncate-to-one-tool-call defence. Nova's own retry loop is not used.
- `llm/parity_test.go` runs one table against both backends: usage/cache/cost mapping, request body shape
  (model, temperature, max_tokens, tool_choice, parallel_tool_calls, provider.order, session_id, reasoning),
  empty content on tool-call messages, batched tool calls, streaming callback, fallback on 500, no fallback
  on 401. All green on both.
- **Live check:** real call through the Nova backend against OpenRouter — text completion, tool call, usage,

### Step 7 — `RunLoop` on Nova's agent

- `agent_engine/nova.go` implements the same `EngineConfig`→`LoopResult` contract on `agent.New(cfg).Run`.
  `engine.backend` (plus `engine.backend_overrides` per agent) selects it; the legacy body is untouched.
- Hooks mapped: `PreIteration`→`BeforeTurn`, `PostIteration`/`<think>`/`OnNoToolCalls`→`MessageEnd`,
  `PostToolResult`/`PostTool`/trace/lite/TUI→`ToolResult`, done + continuation windows→`TurnEnd`,
  `ToolChoiceFirst`+deferred tools→`BeforeProviderRequest`, `OnLoopStart`/`OnLoopExit` around the run.
- `ActiveToolGuard` and `PreTool` live in a `guardedTool` wrapper, not in Nova's permission layer, because
  Nova's blocks return different wording and prompts/sims depend on the exact her-go strings.
- **Metrics:** `llm.Client.Stream` (added so a `*llm.Client` *is* a `provider.Provider`) calls a
  `ResponseHook` after every response, which is how one metric row per provider call — model, provider,
  tokens, cache, cost, fallback — survives Nova only reporting per-run totals.
- **Parity suite:** every existing `engine_test.go` case now runs against both backends (`forEachLoopBackend`).
  Twelve of thirteen pass with no assertion changes. The three that differ are pinned per-backend with a
  comment rather than skipped — see D1, D4, D10 below. `agent_engine/nova_parity_test.go` adds eight cases
  the old suite lacked: malformed args, error results not aborting, `PostToolResult` changing the error flag,
  batched calls running only the first, phantom (empty-name) calls, recovered panics, `tool_choice: required`
  answered with text, and inline `<think>` extraction.
- **Deltas found while testing (recorded, not hidden):**
  - **D1** (as predicted): `PostIteration` cannot break before the tool batch. The run ends right after one
    harmless batch instead. Pinned.
  - **D4** (as predicted): `OnNoToolCalls` cannot ask for another iteration; the text is still captured.
    Pinned. No caller uses the return value.
  - **D5** (stronger than expected): Nova validates tool arguments against the schema *before* dispatch, so
    a truncated argument list produces Nova's `error: invalid arguments: ...` rather than her-go's
    `error: malformed JSON in arguments ... (likely truncated by token limit)`. Same outcome (error result,
    loop continues), different words to the model. Recorded in `NOVA-GAPS.md`.
  - **D9** (improvement): the legacy loop advertised only its starting tool set, so `use_tools` loaded a tool
    that was callable but not in the schema. The Nova path re-advertises `ActiveTools` every turn, so loaded
    tools now appear in the schema too. Deliberate; flagged for Autumn in the PR.
  - **D10**: a guarded/rejected call counts as a tool call in `LoopResult.ToolCalls` and produces a trace
    line, because it passes through Nova's per-call result hook. Same model-visible error string.
  - **D11**: truncated tool arguments are a retriable transport error in the legacy client (fallback model
    gets a try) but a normal tool error result in the Nova path (the model retries itself). Safe either way.
  - **Out of reach:** `ExitFinishReasonStop` (the OpenCode #14972 pattern) cannot be detected, because Nova
    rewrites a `stop` that arrives with tool calls to `tool_calls`. The run then ends on the next turn, which
    is the same observable outcome as the legacy loop for the same input.

### Step 8+9 — single cut, and the legacy loop deleted

- **Staged per-agent cutover (step 8) folded into one cut**, at Autumn's direction: with one loop implementation
  there is no per-agent switch to stage with. The per-agent risk the plan worried about — does *this* agent use a
  hook Nova cannot reproduce? — is covered by the parity suite instead, which exercises every hook the five
  agents actually register. Rollback is per-process (`llm.backend: legacy` for the transport), not per-agent.
- **Legacy loop deleted** (`agent_engine/engine.go` −394 lines, plus the backend flag, the `engine:` config
  section, the per-agent overrides and the `--engine-backend` sim flag). `RunLoop` survives as a one-line
  wrapper and the package still owns `EngineConfig`/`LoopResult`/exit reasons/`BuildContinuationSummary`/
  `TruncateLog`, because those are the contract the five agents were written against.
- **Legacy LLM transport kept**, defaulted to `nova`, as the rollback lever the plan allowed for: deleting it was
  conditional on soaking, and the 28 non-loop call sites (reply streaming, classifier, mood, vision, compaction,
  fast path) have parity tests but no production soak yet. Deleting it is the follow-up.
- **Bug the sims caught (this is why they exist):** the Nova registry was built from the YAML manifests alone,
  but `use_tools` never appears in a manifest — `HotToolDefs` synthesises it. The driver therefore got
  `unknown tool "use_tools"` on every call, could not load a single deferred tool, told the user it had no way to
  schedule anything, and the chat model filled the gap with invented `<tool_call>` markup. Fixed by registering
  the *union* of the caller's defs and the agent's manifest defs, with a regression test
  (`TestNova_RegistryIncludesCodeOnlyTools`). The first Nova `schedule-crud` digest was discarded because of it.
